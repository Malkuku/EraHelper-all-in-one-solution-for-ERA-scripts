# MVU 手动发布准备

## 目标与范围

用户确认日常提交不向玩家发布，正式版本由维护者手动发起。本轮落实发布准备：统一当前版本资料、生成可核对的完整脚本候选包，并提供仅手动触发的 GitHub Actions 验证/打包入口。

首轮本地阶段不创建远程分支、标签或 Release；后续用户要求继续，扩展到最小默认分支入口接入和云端候选验证，范围见后续远端接入记录。默认分支业务源码保持原样，不接入在线加载器、客户端检查更新或最新版本公告。候选包不等于正式发布；实际酒馆验证与既有许可组合待确认，不能据本地通过宣称已完成对外分发。

## 关键设计决定

- 当前版本唯一资料源为 `src/MVU助手/release.json`：version（不含 v 的三段正式版本）、date（YYYY-MM-DD）、changes（非空说明数组）。关于页当前版本与首条历史、候选包说明共用该资料。历史 1.x 日志保留。
- 专用 `prepare-mvu-release.yaml` 仅 `workflow_dispatch`，在选中分支执行，使用 Node 24、pnpm 11 和 frozen lockfile。日常 push 不产生正式版本。
- 旧 bundle 工作流不再自动生成/删除标签；保留原有分支范围内的构建用途，不改其他模板同步职责。
- 候选包输出到被忽略的 `dist/mvu-release/`，包含 `index.js`、对应 sourcemap（若 bundle 引用必须存在）、`release.json`、`release-notes.md`、`SHA256SUMS`。发布元数据包含版本、来源仓库、完整源码提交标识和文件摘要；不生成指向不存在文件的 CDN 地址或 latest 公告。
- 本地 `pnpm release:prepare` 先校验资料，再构建、打包；CI 运行既有五个确定性入口与打包契约测试后，执行相同命令并上传版本命名的候选 artifact。
- 打包严格验证版本、日期、说明、仓库身份与源码 SHA；缺少/空脚本、损坏资料、缺少被引用 map 或验证失败必须非零退出，不产生看似完整的新候选包。
- 打包接口允许测试传入临时根目录和明确来源信息；正常 CLI 读取当前 checkout 的 Git SHA，正式仓库固定为关于页仓库。离线测试不需要访问 GitHub。
- 来源记录同时包含构建前工作区是否有未提交内容。开发中的本地候选可以生成，但必须标明 dirty，不能声称源码仅由 HEAD 精确重现；全部候选明确标为 candidate，不代表已发布。
- 完整脚本仍依赖酒馆和现有远程运行依赖；不宣传为离线独立程序。手动安装沿用原脚本 ID 更新代码，保留配置与密钥关联。

## Agent 分工与测试所有权

- 父 Agent：资料源/关于页调整、Spec 与使用说明、交付物审阅及收口。
- 发布实现 Agent：候选包工具、仅手动工作流、package 命令与旧自动标签退出；最小实现自测。
- 独立测试 Agent：从上述契约独立审阅并验证候选包成功/失败、可追溯性、工作流触发和相邻页面；发现缺口时在 `tests/release/` 建立唯一主要入口，不复制业务 suite。

## 验收标准与验证范围

- 当前版本/首条更新记录/候选资料一致，版本仍为 2.0.0。
- 日常 push 无正式发布、无自动打标签或删标签路径；新工作流只手动准备候选 artifact。
- 真实生产构建打出的脚本、map、说明及摘要记录相同源码基线与 dirty 状态，可用摘要核对。
- 非法资料、缺失文件或打包失败明确报错；失败不能保留一个冒充本次成功的完整包。
- 定向工具测试、五个既有确定性入口、关于页模拟宿主断言、定向 ESLint、真实 `release:prepare`。
- GitHub Actions 实际远端运行、完整脚本真实酒馆加载和正式发布仍为外部门禁。

- 关于页重复维护的当前版本和当前发布说明，改为共用 JSON 资料。
