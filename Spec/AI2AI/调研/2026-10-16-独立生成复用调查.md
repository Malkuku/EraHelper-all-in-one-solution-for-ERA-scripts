# 独立生成复用调查

## 目标与调查范围

判断原版宿主能否接受任务自己的预设副本、世界书候选池和扫描上下文，完成提示词组装并返回结果，同时允许任务之间以及任务与主聊天并发。本文记录源码调查，不是已实施架构，也不代表运行环境验收通过。

调查日期：2026-10-16。固定源码版本：

| 项目 | 版本 / 提交 |
| --- | --- |
| SillyTavern | 1.19.0，`06bde939fb1e9c4c8d8641d810f0a916b5bce127`，release 分支快照 |
| 酒馆助手 | 4.11.3，`333e8a13dfabca359d0105cd0f3c90e9d341ea52`，main 分支快照 |
| ST-Prompt-Template | `d6f520d149aba146305b0b781ddd691d449c28d2` |
| ST-CustomGeneration（参照实现） | `90e62bc1eaaf193f21b5ebd6c32dd47af6ed1911`，按该 HEAD 调查 main 下载快照 |

尚未确认玩家实际安装的版本。仓库 `@types/function/generate.d.ts` 比调查的酒馆助手接口旧，不能据本地类型缺少字段推断上游不支持。

## 结论

在上述入口与调用链中，没有找到同时接收独立预设对象、独立世界书候选池，并完成完整模板处理和并发生成的现成入口。

可以复用独立请求服务、宏替换及 EJS 文本渲染。主要缺口在按任务运行的世界书扫描和提示词组装；只替换 fetch 或取消本插件生成锁不能解决它们。

| 职责 | 已有能力 | 对本项目的判断 |
| --- | --- | --- |
| 预设读取、格式转换 | 酒馆预设管理及酒馆助手 getPreset | 可借鉴；酒馆助手规范化 Preset 与酒馆原生导出 JSON 不是相同结构，导入导出应保留原生字段 |
| 原生宏 | getContext().substituteParams 等 | 可调用；继续读取当前聊天环境，按已接受的共享读取风险处理 |
| 世界书扫描 | getWorldInfoPrompt / checkWorldInfo | 没有候选池参数，需要抽取或移植其相关职责 |
| 预设提示词排序、深度插入和预算 | prepareOpenAIMessages / PromptManager | 依赖全局实例，不能只传预设副本就隔离运行 |
| EJS 文本渲染 | EjsTemplate.prepareContext / evalTemplate | 可调用，但不能替代扩展完整生成阶段处理 |
| 已组装消息的发送 | ChatCompletionService.sendRequest | 可复用，绕开主聊天生成流程；也可自己 fetch 同源后端或模型服务 |

## 酒馆：发送层已有独立入口，扫描层仍绑定全局数据

`getWorldInfoPrompt(chat, maxContext, isDryRun, globalScanData)` 调用 `checkWorldInfo`；扫描器内部调用无候选池参数的 `getSortedEntries()`，读取当前聊天、角色、玩家和全局世界书。第四参数是扫描附加文本与触发类型，不是条目数组。扫描还读取 extensionPrompts，使用全局外部激活表，更新 `chat_metadata.timedWorldInfo`，并可能写作者注释。`isDryRun` 也不会使整条链成为无状态函数。

证据：[候选池加载和扫描](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/world-info.js#L4590)、[扫描后的状态处理](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/world-info.js#L5265)。通过 WORLDINFO_ENTRIES_LOADED 临时替换条目仍是共享事件路径，缺少逐请求身份，不能作为候选池隔离方案。

`prepareOpenAIMessages` 虽接收消息、世界书文本等，却从全局 promptManager 读取顺序和预算，调用私有组装函数，随后更新该管理器和 UI。新建一个 PromptManager 实例也不能改变函数内部引用的全局实例。底层 ChatCompletion / Message 等可借鉴，但也共用 tokenHandler 等能力，不能直接宣称完全独立。

证据：[提示词组装入口](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/openai.js#L1542)。

`getContext().ChatCompletionService` 提供：

- `presetToGeneratePayload(preset, overridePreset, overridePayload)`：接受预设对象和已组装消息，转换生成参数；不会把预设提示词组装进 messages。
- `sendRequest(payload, extractData, signal)`：将已经组装的载荷发往同源 `/api/backends/chat-completions/generate`，使用调用方信号或本次独立 AbortController；该方法不进入主聊天生成入口，也不调用完整 EJS 处理链。

证据：[独立请求服务](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/custom-request.js#L421)。参数转换仍以当前 oai_settings 的深拷贝补默认值；其下游 createGenerationParameters 还涉及全局 logit bias 缓存、停止词、工具注册和部分源校验，所以不能把整个转换过程视为纯函数。

同源后端的常规请求分支使用本次请求的消息、连接字段和 AbortController：[后端处理](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/src/endpoints/backends/chat-completions.js#L2242)。这说明主聊天的前端互斥并非发送 HTTP 的必要条件；不等于已验证所有源的并发行为。复用此后端也是可选传输路径，不要求修改酒馆，也不要求模型服务支持浏览器 CORS。

## 酒馆助手：并发控制有改进，世界书隔离仍缺失

4.11.3 的 generate / generateRaw 使用逐 generation_id 的控制器；`should_silence: true` 能避免绑定主聊天停止按钮及对应 UI 阻塞。命名 `preset_name` 会转换为 ordered_prompts / injects 和部分生成参数，而不是全局切换预设。版本最低要求尚未调查，不据此要求用户升级。

但是 `prepareAndOverrideData` 仍设置共享 extension_prompts，包括固定键 TEMP_USER_MESSAGE 和深度注入，并调用原版 getWorldInfoPrompt。生成类型未提供候选条目参数，世界书文本 overrides 在扫描之后应用，因此不能绕过前面的扫描副作用。响应阶段也存在共享事件和前缀清理。

证据：[配置与控制器](https://github.com/N0VI028/JS-Slash-Runner/blob/333e8a13dfabca359d0105cd0f3c90e9d341ea52/src/function/generate/index.ts)、[世界书数据准备](https://github.com/N0VI028/JS-Slash-Runner/blob/333e8a13dfabca359d0105cd0f3c90e9d341ea52/src/function/generate/dataProcessor.ts)、[响应处理](https://github.com/N0VI028/JS-Slash-Runner/blob/333e8a13dfabca359d0105cd0f3c90e9d341ea52/src/function/generate/responseGenerator.ts)。

因此“酒馆助手声明支持并发”成立，但不能推出“不同任务候选池与正文隔离”。当前项目的全局过滤和预设切换还会在这些共享点上叠加风险。

## 提示词模板：渲染入口可用，完整阶段需要任务调度

宿主全局 EjsTemplate 暴露 prepareContext 和 evalTemplate，可不触发主聊天生成而渲染文本。完整生成链还处理扫描前条件与预处理、GENERATE 前后条目、正则、@INJECT、outlet 和清理；这些操作在 handler 中，没有同等的完整全局处理入口。

prepareContext 会刷新共享变量缓存；variables 是共享 STATE.cacheVars 的 getter。getpreset 默认读取宿主预设内容，不知道插件导入的副本。因此需要给任务上下文适配预设读取，不能把“允许读取当前聊天状态”扩大为“允许错读主聊天预设”。特殊条目枚举也必须改为任务候选池，显式 getwi 按用户决定允许读取池外。

证据：[公开接口](https://github.com/zonde306/ST-Prompt-Template/blob/d6f520d149aba146305b0b781ddd691d449c28d2/src/modules/exports.ts)、[上下文及预设读取](https://github.com/zonde306/ST-Prompt-Template/blob/d6f520d149aba146305b0b781ddd691d449c28d2/src/function/ejs.ts#L211)、[完整阶段处理](https://github.com/zonde306/ST-Prompt-Template/blob/d6f520d149aba146305b0b781ddd691d449c28d2/src/modules/handler.ts#L212)。

不能靠主动广播酒馆全局生成事件来复用完整模板链：那会让主聊天及其他监听器一起执行，重新引入候选池和生成状态混用。已接受的模板共享读取窗口不代表接受这些结构性串扰。

## 参照：ST-CustomGeneration 并未提供完全隔离的捷径

提示词模板作者的另一扩展 ST-CustomGeneration 公开 Context、PromptContext、MessageBuilder 和 buildMessages 等能力，支持独立预设和并发子任务，可作为设计参照。

但其 Context.generate 在消息组装时使用模块级 AsyncMutex，临时交换全局 chat_metadata.timedWorldInfo，并注册 WORLDINFO 事件处理器；PromptContext.scan 最终仍调用原版 getWorldInfoPrompt。互斥锁保护的是该扩展内部调用，未证明能保护原版主聊天。公开 buildMessages 也没有显式候选池参数。

证据：[公开对象](https://github.com/zonde306/ST-CustomGeneration/blob/90e62bc1eaaf193f21b5ebd6c32dd47af6ed1911/src/index.ts#L33)、[生成上下文](https://github.com/zonde306/ST-CustomGeneration/blob/90e62bc1eaaf193f21b5ebd6c32dd47af6ed1911/src/features/context.ts#L488)、[扫描入口](https://github.com/zonde306/ST-CustomGeneration/blob/90e62bc1eaaf193f21b5ebd6c32dd47af6ed1911/src/functions/prompt-context.ts#L32)。本次未将它安装到用户环境，也不据此引入新依赖。

## 补充调查：保留组装串行，在可信窗口解锁

用户随后提出优先考察短锁方案：继续使用宿主组装，形成独立请求后恢复共享配置并释放组装锁，让网络等待并行。此前独立组装方案保留为替代路线。以下仍是静态调查，不是短锁已完成的证明。

### 正常路径存在明确的代码边界

已检查的 OpenAI Chat Completions 路径依次执行：生成参数组装、await CHAT_COMPLETION_SETTINGS_READY 的事件派发、JSON.stringify 请求载荷、fetch。提示词模板扩展在该事件中完成最终 EJS 与注入处理。因此候选释放点应放在本次派发的最后一个相关监听器完成后，而非看到事件的任意监听器时；此时并不需要等待模型返回。

证据：[原版发送函数](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/openai.js)、[扩展最终处理入口](https://github.com/zonde306/ST-Prompt-Template/blob/d6f520d149aba146305b0b781ddd691d449c28d2/src/modules/handler.ts#L201)。结论限定于所检查路径，不据此覆盖其他后端。

酒馆 EventEmitter.emit 在开始时复制监听器列表，再逐个 await；makeLast 可将监听器移到注册列表末尾。若能确保本次派发的快照中，我们的释放监听器排在所有相关处理器之后，则有一个可考察的末尾窗口。makeLast 不是永远最后的优先级，后续注册会改变未来派发顺序；派发进行中重排当前注册列表也不会改变已经复制的快照。原生 once 包装不返回内部监听器 Promise，不能用异步 once 充当可靠屏障。

证据：[事件派发器](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/lib/eventemitter.js#L62)。固定延迟不能证明监听器已经完成；被监听器启动但未返回或 await 的后台工作也不在此屏障内。

### 解锁之前仍需解决的三个问题

1. **归属和准入**：SETTINGS_READY 不带 generation_id。可以研究以唯一组装锁持有者归属事件，但前提是主聊天和所有纳入范围的任务都在读取共享状态前经过同一准入规则。其他绕过准入的生成、dry-run 等不能被误认成当前请求的完成信号。4.11.3 的 js_generation_requested 带任务 ID 且会被 await，可用于该版本助手任务的准入；不能当作旧版本已经具备的接口。
2. **异常及重入**：原版 GENERATION_STARTED 之后存在命令中断、连接检查返回、ping 失败等提前退出；没有覆盖整段前置流程的统一 finally。GENERATION_ENDED 由隐藏停止按钮的逻辑发出，不足以证明所有早退都有对应事件。本项目 MESSAGE_SENT 还会 await 负 order 任务，且此时主聊天已发出 GENERATION_STARTED；若主聊天已持锁而负 order 任务等待同一锁，会死锁。需要明确的交接或重入设计，不能只添加两个事件监听器。
3. **延后写回**：本项目预设到整链结束才恢复，Profile 在 generate 返回后恢复；提前开放新组装后，这些旧任务的恢复操作可能覆盖新持有者状态。酒馆助手响应阶段也有共享 stream_openai 恢复和注入清理。必须核对并调整这些生命周期，不能假定释放组装锁以后整个旧调用都不再碰共享状态。已接受的 EJS 共享读取风险不自动覆盖预设、过滤配置被覆盖的问题。

证据：[原版生成入口及早退](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/script.js#L4291)、[助手响应收尾](https://github.com/N0VI028/JS-Slash-Runner/blob/333e8a13dfabca359d0105cd0f3c90e9d341ea52/src/function/generate/responseGenerator.ts)、本仓库 AsyncAnalyzeTaskRunner.ts 与 AsyncAnalyzeService.ts。

### 当前判断

短锁值得优先考察，正常成功路径有源码支持的候选窗口。但尚未证明在原版宿主、现有预设/Profile 行为和现有触发方式下，可以只用公开事件完整实现准入、恢复与异常释放。下一步应围绕这三个问题做最小设计与目标环境验证；不能把“末尾监听正常触发过”写成完整并发验收。

## 独立组装路线的实现边界（备选，待实施设计）

1. 建立任务自己的生成上下文，消费插件预设副本、候选条目副本和配置的扫描历史。
2. 抽取或移植世界书扫描及预设组装职责，显式传入候选池、预算、扫描配置和时序状态；避开宿主全局过滤与预设切换。
3. 尽量调用宿主宏与扩展 EJS 渲染；补齐任务阶段调度和副本预设读取，特殊条目使用任务候选池。
4. 发送已组装消息时，可选现有决定的模型直连 fetch；也可根据本次证据改选原版同源后端或 ChatCompletionService.sendRequest。传输选择不改变前述组装缺口，尚未替用户更改决定。

需要在实施设计中明确世界书 sticky/cooldown/delay 的任务状态和楼层依据，以及预设缺省字段、宏的任务输入覆盖和正则来源。不能以简化“关键词匹配”替代用户要求的酒馆扫描语义。

本次完成源码静态调查；未运行模型请求、并发实验、EJS 运行验收或业务测试。下一步最有价值的是在目标宿主版本验证“独立候选池扫描 → 预设组装 → EJS → 两任务与主聊天同时生成”的最小闭环，再据实际差异确定移植边界。
