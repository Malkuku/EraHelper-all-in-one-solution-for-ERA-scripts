# 任务生成隔离方案

日期：2026-10-16。

状态：2026-10-17 已完成生产路径迁移、确定性独立验收与开发/生产构建，待实际宿主验收。用户授权在源码调查后权衡并选择方案；源码依据见 [独立生成复用调查](../调研/2026-10-16-独立生成复用调查.md)，运行证据见 [验收记录](../迭代任务/2026-10-16-独立生成验收记录.md)。

执行任务：[独立生成与并发任务重构](../迭代任务/2026-10-16-独立生成与并发任务重构.md)。触发、结果、回滚和密钥的已确认边界见 [目标契约](../API/分步任务目标契约.md)。

## 破坏性更新授权

用户于 2026-10-16 明确允许完全不兼容旧版本，以代码干净性为基准。旧配置、生成路径和仅有兼容职责的抽象可直接退出；不要求自动迁移，不保留旧 API 别名和双轨入口。原生酒馆预设导入导出仍是明确的产品要求。该授权不涉及无关模块和用户正文、世界书数据的清空。

## 决定

采用任务独立组装的生成链，复用原版酒馆的数据读取、宏和提示词模板扩展的渲染能力。任务持有自己的预设副本、世界书候选池、扫描上下文、组装结果和取消控制器。世界书扫描与预设组装中绑定全局状态的职责，按酒馆规则抽取或移植到任务上下文。

发送层优先由插件 fetch 原版酒馆同源 Chat Completions 后端，提供本次任务完整的消息、生成参数和连接字段，复用其请求转发与协议处理。它不调用主聊天 Generate 或酒馆助手完整生成链。此决定替代此前“浏览器必须直接请求模型服务”的传输选择：独立请求的关键是逐请求数据和生命周期，不要求绕开原版后端。

删除 Profile 模式，不再通过全局 Profile 或 loadPreset 切换为任务配置环境。

## 权衡依据

| 路线 | 初始成本 | 达成并发隔离的约束 | 选择 |
| --- | --- | --- | --- |
| 保留完整生成锁 | 最低 | 网络等待仍串行 | 不满足目标 |
| 原生成链组装串行，发送前事件后解锁 | 正常路径改动较少，完整异常处理成本不确定 | 需要统一主聊天准入、可靠事件归属、末尾监听顺序、早退清理、负 order 重入及返回后的共享清理 | 不作为主方案 |
| 任务独立组装，复用基础能力和原版后端 | 前期工作最多 | 可直接控制任务输入、组装和发送边界，减少对其他插件监听顺序与主聊天退出事件的依赖 | 采用 |

删除 Profile 模式只去掉一类共享状态切换，不能消除世界书过滤、全局预设、宿主注入和生成收尾操作的竞态。短锁方案的优势主要在成功路径；上述依赖在原版宿主环境中仍没有已经验证的完整协议。独立组装更符合本项目长期并发目标。

## 已确定的业务边界

- 使用酒馆原生预设格式。导入后由插件长期保存副本，预设提示词和生成参数以副本为权威来源。连接地址、密钥和模型名来自任务 API 配置。
- 支持预设导入导出、同名覆盖提示，以及常见参数、提示词内容、启停和排序的轻量编辑；保留未知字段。高级编辑可在酒馆完成后重新导入。
- 不自动注入角色描述、性格、场景和示例对话等角色卡提示词，也不自动加入玩家人设与作者注释；保留宏以及模板主动读取这些数据。
- 世界书摘取后形成独立候选池，任务内强制启用后按酒馆规则正常触发。扫描上下文来自任务配置，主聊天条目启用状态不被改动。
- 新版本不提供插件“正文配置”或正文专用过滤。旧规则组正文 world_book 字段、配置 UI、过滤事件监听及共享状态全部退出，不重建为独立正文过滤模块；规则组仅承担任务组织职责，世界书候选池仅属于任务。
- 世界书特殊条目，包括 GENERATE 前后处理，自动处理范围同样限定为任务候选池；模板显式 getwi 可读取池外条目。
- 尽量复用酒馆宏与 ST-Prompt-Template 渲染。由任务调度其处理阶段；模板内的预设读取应指向任务副本，不能误读主聊天预设。不广播全局生成事件来模拟完整宿主调用。
- 首版处理 OpenAI 兼容 Chat Completions 文本任务。原版后端虽支持其他源，不因此扩大首版协议范围。
- 保留已经确认的事件结果、输出方式、冲突检测与回滚要求。生成独立不意味着提交可以覆盖其他任务的结果。

## 可接受风险与实现要求

用户已接受宏和 EJS 读取当前聊天数据时的短窗口不一致，以及提示词模板扩展可用性的部署风险。该接受不覆盖预设、候选池和请求载荷串扰。

复用后端时必须显式映射任务连接和参数，不能无意继承主聊天模型或密钥。以源码调查支持的同源请求能力为设计依据，目标安装版本的请求字段、鉴权和响应格式仍需验证；不静默回退为主聊天生成或全局配置切换。

世界书规则移植包含递归、预算、分组、位置与时序效果语义，不能以简单关键词过滤替代。sticky/cooldown/delay 的存储、楼层依据、成功合并与回滚所有权已在详细契约中冻结并实现；已接受的 EJS 风险不能代替这一契约。

## 验证范围与证据边界

实施按任务上下文和最小闭环、配置 UI、提交调度、生产接线依次推进。验证覆盖：

1. 两个任务分别使用不同预设、候选池和连接配置，与主聊天同时运行，核对最终载荷归属。
2. 预处理 EJS、普通模板、特殊注入与显式池外读取符合既定范围；模板读取预设副本。
3. 任务取消、请求失败和负 order 任务不会等待主聊天持有的组装锁，也不会清理其他任务状态。
4. 生成结果仍按已有提交和回滚规则结算。

`tests/async-tasks/` 的 generation、configuration、commit、runtime 四个确定性入口已完成独立反例扩充并通过，覆盖载荷隔离、模板阶段、扫描时序、局部补偿、忙碌隔离和终态快照。开发及生产构建已通过。以上使用可控宿主替身，不代表第 1 项的真实主聊天重叠或真实后端、模板扩展、MVU 环境已验收；实际部署版本和集成证据仍须按验收记录补齐。

提交 Journal 和未恢复日志只保存在当前脚本会话。持久化任务成功历史与时序状态不构成跨重载回滚能力；重载后缺少对应 Journal 的专用重算会明确失败。该边界由运行 API 和用户指南共同说明。
