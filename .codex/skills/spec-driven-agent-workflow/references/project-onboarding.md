# 仓库初始化与既有项目引入

仅在以下场景读取本文档：

- 用户要在新仓库初始化分层 Spec 工作流。
- 仓库缺少 `Me2AI`、`AI2AI`、索引、API 文档或迭代任务结构。
- 用户要把一个已有 CodeBase 引入该工作流。
- 需要根据已有代码反向构建文档树、架构说明、API 文档或初始迭代任务。

## 先判断引入场景

- 新项目初始化：代码很少或尚未开始实现。优先整理产品需求，再创建 Me2AI 与 AI2AI 骨架。
- 轻量既有项目：已有少量模块，架构边界较清楚。可快速扫描入口与结构，反向建立文档树、总体架构和关键 API 文档。
- 复杂既有项目：模块多、入口多、历史包袱多或测试缺失。先建立可导航的项目地图和引入计划，不一次性承诺完整反向文档化。

## 复杂度评估

先粗略评估：

- 入口数量：应用入口、后台任务、脚本、扩展入口和服务入口。
- 模块数量：核心领域、UI、运行时、存储、共享协议和外部集成。
- 外部契约：公开 API、消息/事件协议、数据模型和持久化格式。
- 测试状态：自动化测试、手动验收材料、fixture 或 mock。
- 文档状态：README、设计文档、接口说明、路线图和历史任务。
- 风险程度：用户数据、持久化迁移、权限、支付、安全和生产系统。

根据复杂度选择策略：

- 小型项目：可在一个细节任务中创建基础 Spec 骨架。
- 中型项目：作为一个迭代任务，先产出引入计划和根索引，再逐步补文档。
- 大型项目：拆成多个迭代，先建立文档树和总体架构，再按稳定领域补 API 与测试方案。

## 新项目初始化流程

1. 整理产品目标、目标用户、核心场景、平台边界和首个可验收版本。
2. 创建或草拟 `Me2AI` 产品说明；未经用户授权，不擅自固化仍在探索的产品决定。
3. 创建 `AI2AI` 骨架：根索引、总体架构、测试方案、API 目录、迭代任务目录和模板。
4. 在根索引中建立最小 Spec 文档树，指向现有文档与必要局部索引。
5. 把首个实现目标拆成迭代任务，父 Agent 内部审阅后向用户交付执行摘要，再按主工作流推进。

## 既有项目反向构建流程

1. 读取仓库入口文件和已有文档，识别技术栈、运行入口、模块目录和测试命令。
2. 优先使用文件结构、配置、导出边界和测试分布判断架构；只有必要时读取源码细节。
3. 盘点已有 Spec 和项目级说明，反向创建或补全 `AI2AI/索引` 中的真实文档树。
4. 根索引展开到稳定主题或局部索引；复杂分支建立局部索引，局部索引再展开到具体文档。
5. 创建总体架构说明，描述产品边界、运行模型、模块职责和关键约束。
6. 为稳定模块补 API 文档；不稳定或混乱模块先标记为待梳理，不伪造确定契约。
7. 创建测试方案，记录现有测试层级、缺口、验证入口和推荐的最小充分验证路径。
8. 若需要重构或继续补文档，把后续工作拆成迭代任务；不要把反向梳理隐式扩大为代码重构。

## 文档树初始化边界

文档树的目标是让新 Agent 不扫描整个目录，就能决定下一步读取哪个文档或局部索引。

- 根索引通常展开到“分层 → 稳定主题/领域 → 文档或局部索引”。
- 分支直接子项超过约 7～10 个，或名称无法支持读取决策时，建立局部索引。
- 局部索引展开到具体文档；单份文档内部章节由自身目录负责。
- 节点只写真实路径、清晰名称和必要的一句话用途，不在根索引堆积完整依赖、代码清单或历史细节。
- 当前迭代、阻塞任务和近期待开始任务保留在根索引；完整历史任务进入迭代任务局部索引。

初始化时推荐使用浅树状 `Spec 文档树`，让根索引呈现稳定分区和局部索引入口：

```text
## Spec 文档树

- Me2AI
  - [核心项目说明](../Me2AI/核心项目说明.md)：产品意图、用户价值与业务边界。

- AI2AI
  - [技术选型与总体架构](./技术选型与总体架构.md)：技术栈、运行模型、模块边界。
  - [测试方案](./测试方案.md)：验证入口、测试缺口、最小充分验证策略。
  - API
    - [API 索引](./API/README.md)：外部接口、远程模块、领域 API 文档入口。
  - 迭代任务
    - [迭代任务模板](./迭代任务/模板.md)：后续任务文档格式。
```

不要在根索引中展开所有 API 文档或源码目录。API 数量多时，使用 `AI2AI/API/README.md` 作为局部索引，并按业务领域或契约边界继续分层，例如：

```text
Spec/AI2AI/API/
  README.md
  公共能力.md
  远程模块.md
  领域A/
    README.md
    子领域或接口组.md
  领域B/
    README.md
    子领域或接口组.md
```

领域目录名称应服务读取决策，可以按业务领域、稳定模块、外部契约边界或高频变更面命名；不要机械复制源码物理目录。每个局部 `README.md` 展开到可直接选择的具体 API 文档，并说明对应源码位置。

可以通过以下问题检查文档树是否足够：

- 修改某个外部契约时，新 Agent 能否直接定位对应 API 文档？
- 修改某个领域行为时，能否找到相关架构、测试和当前迭代入口？
- 是否仍需全文搜索所有 Markdown 或随机打开多份文档才能判断？
- 根索引是否已经长成需要再次全文阅读的大清单？

## 需要询问用户的项目细节

不要一次问太多。优先询问无法从仓库可靠推断、且会影响文档边界或实现方向的内容：

- 项目的核心用户价值是什么？
- 最重要的运行入口或交付形态是什么？
- 哪些模块或行为已经稳定，哪些仍在探索？
- 哪些数据、协议或用户行为必须保持兼容？
- 用户希望先文档化现状，还是同时规划下一轮重构？

可以从 CodeBase 明确推断时，先推断并标注“根据代码推断”，不要把本可完成的仓库理解工作转交给用户。

## 最小初始化产物

- `Spec/Me2AI/核心项目说明.md`
- `Spec/AI2AI/索引.md`
- `Spec/AI2AI/技术选型与总体架构.md`
- `Spec/AI2AI/测试方案.md`
- `Spec/AI2AI/API/README.md`
- `Spec/AI2AI/迭代任务/模板.md`

按项目规模逐步补充：

- 各领域或分层 API 文档及必要局部索引。
- 数据模型、消息/事件协议和持久化格式文档。
- 当前迭代任务文档及历史任务索引。
- 手动验收材料、测试 fixture 和运行说明。

## 注意事项

- 不要为了完整性编造不存在的架构事实或契约。
- 不要把一次反向梳理扩大成隐式重构。
- 不要把历史细节堆入根索引；根索引保留文档树骨架和当前项目快照。
- 不要机械复制物理文件树；文档树应服务读取决策，并通过局部索引控制展开深度。
- 对复杂项目，先建立可导航的地图，再逐步补契约和验证细节。
