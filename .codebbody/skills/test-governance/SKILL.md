# Test Governance

## 定位

测试是工程验证的一环，不追求越多越好。

本 Skill 负责让 Agent 决定：

- 是否需要测试；
- 测到什么程度；
- 是否需要独立 Test Agent；
- 已有测试在哪里；
- 新测试应放在哪里；
- 新旧测试是否需要收敛。

测试需求优先来自 Spec、API / 业务契约、验收标准和 Bug 原始失败案例，不从当前实现反推需求。

## 执行流程

### 1. 先确定要证明什么

读取当前任务所需的 Spec、契约和验收标准。

Bug 修复必须保留原始失败案例。

只把当前实现用于理解验证方式，不把实现细节自动固化成测试契约。

### 2. 选择最小充分验证

先判断 `Need Test?`：

- 机械字段、配置、日志、明确接口适配、契约不变的内部重构，可只做编译、类型检查、已有定向测试或最小 smoke check。
- 用户可见行为、业务规则、错误处理、状态流转、排序分页、权限、解析等变化，需要行为验证。
- API / schema、共享核心逻辑、持久化、事务、并发、一致性、消息、迁移、外部集成等变化，按实际风险扩大验证。

再判断 `Test Scope?`：

```text
直接相关验证
→ 稳定契约测试
→ 受影响相邻能力
→ 模块回归
→ 全量确定性测试
→ 外部 / 环境验证
```

只有上一层不足以覆盖具体失败模式时才继续扩大。

如果无法说明更高强度测试会额外捕获什么现实失败，不升级测试强度。

构建、lint、静态扫描或全量测试通过不能替代行为与契约验证；
测试通过也不能替代运行时约束、监控、灰度、回滚或真实环境验证。

### 3. 判断是否需要独立 Test Agent

独立 Test Agent 不是默认步骤。

在正式验收、稳定外部契约、高风险业务行为、跨模块 / 跨服务变化、复杂实现或任务明确要求独立验收时启用。

低风险机械修改、契约不变的局部重构，通常不需要。

启用时：

1. Test Agent 先读 Spec、任务和验收标准。
2. 在继承实现 Agent 的测试结论前，独立列出应验证行为、风险和失败场景。
3. 再读取测试索引、已有测试和实现代码。
4. 只补真实验证缺口。

实现 Agent 可以并且应该做最小充分自测。

不得让实现 Agent 包办正式独立验收；
不得让 Test Agent 只重跑实现 Agent 的测试后宣称独立验收；
不得为了形式独立永久制造第二套相同测试。

### 4. 先发现已有测试

新增测试前按以下顺序查找：

1. 项目测试索引；
2. 索引指向的主要、辅助和验收测试；
3. 相关生产责任点及已有测试引用；
4. 测试目录、类名、关键词、tag、fixture 或 suite；
5. 项目提供的测试 inventory / scan 结果。

已有测试能够自然承载新场景时，优先修改已有测试。

只有不存在合理稳定归属时才新建测试资产。

### 5. 遵守测试权威路径

测试代码应进入项目定义的 canonical test root 和稳定责任路径。

物理目录表达稳定归属，测试索引表达业务能力与测试资产的多对多关系；两者应能相互导航，但不要求完全同构。

一个稳定测试资产只保留一个权威物理归属，其他能力通过索引引用，不复制平行 contract / acceptance / regression 入口。

新建、移动、重命名稳定测试或修改测试索引时，读取：
`references/test-structure.md`

### 6. 收敛新增测试

`Development`、`Acceptance`、`Regression`、`Reproduction`、`Temporary`、`Migration`
都不是自动永久保留的身份。

迭代结束时，新测试必须明确：

- 保留为稳定主要责任测试；
- 保留为有独立诊断价值的辅助测试；
- 保留为长期验收 / 环境门禁；
- 合并进已有测试；
- 删除。

验收阶段允许暂时重复，但独立性不是永久重复的理由。

出现重复、过期、阶段性测试或用户要求测试清理时，读取：
`references/test-cleanup.md`

### 7. 维护测试索引

测试索引只维护稳定语义，不人工维护完整测试方法清单。

以下情况检查索引：

- 新增、删除、移动、重命名稳定测试资产；
- 测试主要职责或测试层变化；
- 新业务能力形成长期测试。

普通测试方法增加、断言调整或内部重构通常不更新索引。

## 硬性约束

- Bug 修复必须覆盖原始失败案例。
- 外部环境测试必须与默认确定性测试区分；环境不可用时明确记录缺口。
- 不因为存在主要责任测试就压制必要的跨层验证。
- 不因为名称、覆盖率或代码相似就直接判定测试重复。
- 不在未检查已有测试和权威路径前创建新的稳定测试类 / suite。
- 生产代码发生相关变化后，旧验证证据不能继续证明当前实现已通过。

## 完成检查

- [ ] 验证范围是否最小但充分？
- [ ] 更高强度测试是否对应明确失败模式？
- [ ] 是否先发现已有测试再新增？
- [ ] 新测试是否进入权威路径？
- [ ] 独立验收是否真正独立形成判断？
- [ ] 阶段性测试是否完成保留、合并或退出判断？
- [ ] 稳定职责变化后是否同步更新测试索引？
