# Handoff

Handoff 是交给另一个执行上下文继续完成任务的临时交接单，不是长期项目事实源。

接收方可能是：

- 无法访问发送方内容的独立工作区；
- 能访问同一工作区文件，但没有当前 Chat 历史的新 Chat 或 agent。

## 交接模式

先判断接收方能访问哪些上下文。

### 独立上下文

接收方无法访问发送方工作区、Spec、代码或历史对话时，Handoff 必须自包含：

- 直接写出跨边界契约、结果和必要背景；
- 不依赖发送方内部路径才能理解任务；
- 已经确定的接口、字段和行为语义必须直接写清楚，不能只写抽象的“适配”“支持”或结果描述；
- 不猜测接收方的文件、组件或内部实现方式；
- 不为了生成 Handoff 主动调查接收方内部如何实现。

例如，如果双方边界已经确定了 HTTP 接口，应根据当前已知契约写明适用的 URL、Method、请求参数、响应结构、状态语义、Header、空值或兼容行为，而不是只写“前端适配新接口”。

这些属于跨边界契约，不属于对接收方内部实现的干涉。

### 共享工作区

接收方能访问同一工作区，只缺少当前 Chat 历史时：

- 优先引用工作区内已有 Spec、API、任务或其他正式工件，避免重复搬运；
- 补充这些正式材料中没有记录、但完成当前任务必须知道的决策和约束；
- 明确指出接收方应从哪些现有工件继续；
- 不把完整聊天过程写进 Handoff；
- 不因为能够访问同一工作区，就把交接扩展成对接收方内部实现的重新设计。

无论哪种模式，接收方都必须能明确知道：**为什么交接、要做什么、跨边界契约是什么、必须保持什么、如何验收。**

## 使用边界

仅在任务需要跨执行边界继续承接时使用，例如：

- 前后端、设计、运维或共享协议之间同步变化；
- 一个工作区产生的契约需要另一个工作区实现；
- 当前 Chat 的工作需要交给同项目的新 Chat 或 agent 继续。

不用于：

- 完全封闭在当前执行上下文的任务；
- 单纯总结当前对话；
- 已有双方可访问且内容完整的正式任务，无额外交接信息需要补充。

长期知识应进入 Spec、ADR、API、迭代任务、代码或测试，而不是 Handoff。

## 文件

默认维护当前工作区根目录：

`HANDOFF-xxxx.md`

写入前先读取已有文件：

- 同一次交接：更新；
- 已完成或无关：替换；
- 不在一个文件中混合互不相关的接收方任务。

多个独立接收方应分别生成面向各自任务的 Handoff。

## 内容原则

只写接收方完成任务需要的信息。

优先包含：

- 必要背景；
- 契约、字段、接口、行为或结果变化；
- 接收方需要完成的修改；
- 必须保持的兼容行为和范围边界；
- 接收方可独立验证的验收标准。

避免：

- 发送方完整实现过程和 agent 分工；
- 与接收方无关的内部修改；
- 无意义复制正式文档；
- 无依据猜测接收方实现细节；
- 根据常见工程经验自行替接收方补充内部方案。

### 写到边界

Handoff 应完整写到双方执行边界，但不要越过边界。

**边界上的契约要具体。**

如果当前任务已经确定，应写出适用的：

- URL、路由或调用入口；
- 请求方式；
- 请求字段、参数和数据结构；
- 响应结构；
- 状态码和错误语义；
- Header、鉴权或调用约束；
- 字段默认值、空值和兼容语义；
- 事件、消息或其他跨服务协议；
- 必要的调用、部署或版本顺序。

不要因为“不能替接收方设计实现”，就把这些已经确定的契约细节省略成一句结果要求。

**边界以内的实现由接收方决定。**

除非某个内部实现本身就是已经确定的跨边界约束，否则不要替接收方规定：

- 修改哪个类、组件或文件；
- 使用什么状态管理、封装或代码组织；
- 如何扫描、分页、聚合或持久化内部数据；
- 如何实现重试、恢复、并发或事务；
- 删除、移动或重构哪些内部工具。

接收方根据 Handoff 中的契约和结果要求，结合自己的上下文完成这些工作。

因此判断标准不是“具体内容能不能写”，而是：

> **这是双方共同依赖的边界契约，还是接收方自己的内部实现？**

前者应尽量写清楚，后者不要代替接收方决定。

### 两种极端反例

**反例一：越过边界，替接收方设计实现。**

已知变化只是后端提供了新的文件读取接口。

错误 Handoff：

> 前端新增 `fileProxy.ts`，统一封装请求；修改 `PptViewer.vue` 使用该工具；增加缓存避免重复请求，并删除原有 OSS 读取逻辑。

这里把跨边界变化扩展成了前端内部代码结构、封装方式和缓存方案。

正确方向是写清楚已经确定的接口契约，例如：

> PPT 文件改为通过新的文件代理接口读取。  
> `GET /files/{id}`  
> 成功时返回文件内容；不存在时返回 `404`。  
> 前端不再直接使用原 OSS URL 请求该文件。

至于前端在哪个组件调用、如何封装请求、是否增加缓存，由前端结合自身实现决定。

---

**反例二：停在边界之前，遗漏必要契约。**

错误 Handoff：

> 前端适配新的文件代理能力，确保 PPT 可以正常读取。

这虽然没有干涉前端内部实现，但接收方仍然不知道实际应该调用什么，也无法直接执行。

如果当前任务已经确定 URL、请求和响应，就必须把这些内容写出来。

“不要替接收方设计内部实现”不能被解释成“只描述高层结果”。

---

字段、接口、枚举或行为变化时，优先使用修改前 / 修改后的差异表达，并注明默认值、空值、兼容方式、版本或部署顺序等必要语义。

任务不能只写“同步”“适配”“保持一致”，应明确到接收方能够定位需要修改的功能边界。

这里的“明确”既不能停留在抽象结果，也不要求深入接收方内部实现。

## 最小结构

```md
# Handoff

## 交接目标
- 来源：
- 接收方：
- 任务主题：

## 背景
...

## 变化与已确认结论
...

## 接收方任务
- ...

## 必须保持
- ...

## 验收标准
- ...

## 参考（如果为同工作区）

- 可指向接收方能够访问的 Spec、API、任务、代码或提交），独立上下文中，正文不得依赖这些引用才能理解任务；共享工作区中，可以用引用代替已经存在的详细事实。

```

## 生命周期

发送方生成 Handoff  
→ 接收方读取并执行  
→ 稳定结论写入正式工件  
→ 验收完成后删除 Handoff

`HANDOFF.md` 是临时交接入口，不应长期保留造成重复执行。
