# Spec 驱动 Agent 工作流

## 定位

把仓库视为由持续演进的 Spec 驱动的长期工程。

先理解已有产品事实、工程契约和任务边界，再决定讨论、直接修改或进入迭代流程。

本 skill 只定义工作流，不保存项目事实。

## 事实来源

项目长期事实由仓库中的 Spec 管理，不要求固定文档层级。

常见内容包括：

* 核心项目说明、产品定位和业务规则。
* 架构、模块边界和技术约束。
* `AI2AI/API`：接口、数据模型、消息协议、持久化等外部契约。
* 迭代任务：当前实施目标、设计决定、分工和验收记录。
* CodeBase：当前实现事实。
* Tests、构建和运行结果：验证证据。

原则：

* 尚未形成结论的讨论不属于稳定项目事实。
* 产品、业务和架构 Spec 可以随开发产生的新决策持续更新，不默认只读。
* Spec 与实现冲突时明确记录实现偏差或 Spec 漂移，不自行抹平。
* 已失效的旧结论应更新或删除，不能因历史文档存在就继续约束实现。

## 索引与文档树

`AI2AI/索引` 是查代码前的主要导航入口，维护稳定 Spec、当前任务和迭代进度。

文档树只登记真实存在的内容，例如：

```text
- [核心项目说明](./核心项目说明.md)：产品定位与长期边界。
- [业务规则](./业务规则.md)：稳定业务行为和产品约束。
- [技术选型与总体架构](./技术选型与总体架构.md)：技术栈与模块边界。
- [测试方案](./测试方案.md)：测试入口与验证策略。
- API
  - [API 索引](./API/README.md)：模块外部契约。
- 迭代任务
  - [迭代任务模板](./迭代任务/模板.md)：任务文档格式。
```

规则：

* 不为满足模板虚构文档。
* 根索引只保留导航所需的信息。
* 分支过大时建立局部索引。
* 新增、删除、移动或重命名 Spec 时同步维护文档树。
* 当前任务和状态变化时同步维护索引。

仓库缺少稳定 Spec 或索引体系时，读取 `references/project-onboarding.md`。

## 请求分类

默认使用能够完整解决问题的最小流程。

### 讨论 / 规划

询问方案、设计、风险、规则或架构。

读取必要资料并给出判断；没有明确实施要求时不修改代码。

### 细节任务

目标单一、范围明确，当前 Agent 能直接完成定位、修改和验证。

例如：

* 修复明确 Bug。
* 修改局部行为、字段、判断或样式。
* 调整若干直接相关文件。
* 补充对应测试或文档。

不得因为涉及多个文件、需要测试或存在 Spec 就自动升级为迭代任务。

### 迭代任务

涉及多个模块、产品入口、API、数据模型、协议、持久化、核心架构、复杂验收或多 Agent 协作。

按后续迭代流程执行。

执行过程中发现任务实际扩大时重新分类。

## 通用执行规则

* 索引优先，契约优先，必要时再读源码。
* 外部契约变化时同步更新对应 Spec/API。
* 用户可见规则不得由实现自行补全。阈值、距离、数量、排序权重等必须来自已有契约、用户决定或能被现有条件唯一推出的规则。
* 同一业务语义影响多个入口时，先找到权威责任层和全部消费入口，避免在各症状点重复实现。
* 不默认保护历史实现。新机制或新模型成为权威路径后，应重新判断旧代码是否仍有独立职责。

## 权威路径收敛

引入新的统一机制、模型或入口时，完成标准是新路径真正接管职责，而不是旧代码全部成功调用了新 wrapper。

检查：

* 当前唯一权威来源是什么。
* 旧实现是否仍有真实业务、协议或兼容职责。
* 新模型是否又被转换成旧表示，只为继续复用旧流程。
* 新统一层出现后，旧解析、判断和转换职责是否仍完整存在。

真实系统边界可以保留 adapter。

已经失去独立职责的内部 wrapper、转换链和中间表示应删除或吸收。

如果“重构”只是：

```text
新增统一层
→ 旧职责全部保留
```

则不视为完成收敛。

## 最小充分验证

按实际影响选择最小验证范围：

* 局部逻辑 → 定向测试、静态检查或最小编译。
* 单模块变化 → 模块测试和构建。
* 跨模块/API/数据模型 → 必要的契约或集成测试。
* 持久化、协议、基础设施或核心架构 → 对应迁移、启动或集成验证。
* 只有影响广泛或项目明确要求时才运行全套测试。

Bug 修复和用户可见行为修改必须覆盖原始失败案例。

用户已经提供截图、输入输出、错误入口或复现步骤时，应直接用于回归验证。

Lint、typecheck、编译和构建不能替代行为与契约验证。

## 迭代任务流程

父 Agent 负责定界、协调和收口，不替代已经分配的主要实现与测试角色。

### 1. 读取与定界

读取必要的索引、Spec、API 和代码，明确：

* 目标与范围。
* 依赖和风险。
* 验收标准。
* 验证范围。
* 文档更新项。
* 权威责任层。
* 本轮属于新增、兼容扩展还是替代既有机制。

如果新机制将成为某项职责的唯一权威路径，而旧实现没有明确兼容职责，则视为替代。

不要只根据报错文件确定修改范围；先找到该行为真正的责任层。

### 2. 创建任务文档

任务文档至少包括：

* 目标与范围。
* 关键设计决定。
* Agent 分工。
* 验收标准。
* 测试所有权。
* 验证范围。
* 文档更新项。
* 旧机制取缔项，如存在。

命名为yyyy-mm-dd-简短描述.md

同步在索引登记任务状态。

任务文档创建和主要实现不得并行。

### 3. 归档任务文档

只有当用户明确要求归档时，才能将任务进行归档，放入`迭代任务/归档/{按日期或者功能合理聚合}/`。

#### 旧机制取缔项

存在替代关系时，用简短列表说明需要退出的旧职责：

```md
## 旧机制取缔项

- 移除旧四级相关度评分及对应 SQL、常量和测试，由 RRF 统一替代。
- 移除失去职责的旧高亮解析与重新序列化链，由统一段模型作为内部权威表示。
```

只描述语义清理边界，不要求提前列出每个文件。

取缔对象可以包括：

* 旧业务机制。
* 旧解析或转换链。
* 中间表示。
* 配置、SQL、协议入口。
* 只服务旧行为的测试和文档。

确需保留兼容层时，应有明确理由和退出条件。

### 3. 父 Agent 审阅

实现前检查：

* 范围和设计。
* Agent 分工。
* 验收与验证范围。
* 权威路径。
* 旧机制取缔项。

这些内容未确定前，不启动主要实现。

### 4. 用户执行摘要

向用户简要说明：

* 目标理解。
* 关键方案和边界。
* 明确不做的内容。
* 预期交付物。
* 真正需要用户判断的事项。

存在旧机制取缔项时单独展示。

用户确认的是旧职责是否退出，不是审批每个文件删除。

确认后，属于该清理边界的死代码、配置、SQL、测试和文档无需重复审批。

用户已经明确要求执行且没有真实决策项时，不机械等待确认。

以下情况暂停对应实现：

* 会显著改变结果的歧义。
* 范围扩大。
* 不可逆操作。
* 兼容性破坏。
* 核心产品或架构分叉。
* 与用户既有决定冲突。
* 新增未批准的旧机制取缔范围。
* 需要自行定义外部可见规则。

### 5. Agent 分工

任务文档中声明的角色属于完成门禁。

存在独立测试 Agent 时，明确区分：

* `实现自测`
* `独立验收`

实现 Agent 只负责开发所需的最小自测。

正式验收测试由测试 Agent 从 Spec 和验收标准独立推导。

不得：

* 让父 Agent代替已声明角色完成工作。
* 让实现 Agent 包办正式验收。
* 让测试 Agent 只重跑实现 Agent 的测试后宣称独立验收。
* 为形式上的独立性重复制造相同测试。

### 6. 实施

默认优先让同一设计/实现 Agent 完成一个业务闭环。

只有任务真正独立、交付物独立且不会共同修改核心文件时才并行。

存在 API、数据模型、持久化、协议或核心文件依赖时优先串行。

实现过程中：

* 同一业务语义不得在不同入口重新实现。
* 新权威模型建立后，内部调用方优先直接消费它。
* 不得为了继续使用旧加工链，把新模型重新转换成已被替代的旧表示。
* 失去职责的内部 adapter、wrapper 和旧路径应删除。
* 已批准取缔项应沿真实依赖关系完成清理。
* 属于已批准项的具体死代码无需再次审批。
* 发现新的独立取缔范围时重新进入决策。
* 不得通过扩大阈值、增加模糊 fallback 或兼容分支擅自填补需求缺口。

### 7. 测试与收口

测试 Agent 按 Spec 独立验收，重点覆盖：

* 用户原始失败案例。
* 明确输入输出样例。
* 实际发生问题的入口。
* 关键边界及相邻反例。
* 外部契约和失败路径。

存在旧机制取缔项时，还要验证：

* 旧行为不能继续从生产入口生效。
* 旧实现没有继续作为另一条权威路径存在。
* 旧配置、SQL、协议和中间表示没有继续承担被替代职责。
* 旧测试和稳定文档已经删除或更新。

关键词和调用检索只能作为辅助证据。

父 Agent 只审阅交付物和证据，不重复仍然有效的测试。

测试后代码发生相关修改时，对应验证证据失效，应重新验证受影响范围。

### 8. 文档与状态收口

任务状态跟随真实进度，例如：

```text
待开始
→ 待关键决策
→ 进行中
→ 实现完成待测试
→ 测试完成待收口
→ 已完成
```

项目可使用自己的等价状态。

完成时：

* 填写任务文档完成记录。
* 更新索引和当前迭代状态。
* 更新发生变化的长期 Spec。
* 更新外部契约文档。
* 删除或改写已经失效的稳定描述。
* 按项目要求提交 git。

讨论或实施过程中形成新的稳定产品事实、业务规则或架构决定时，应沉淀到对应长期 Spec，而不是只留在聊天或迭代任务里。

## 硬性约束

* 任务文档、执行摘要和验证范围未确定前，不启动迭代主要实现。
* 不得把任务文档创建和主要实现并行。
* 有核心依赖的任务不得为了并行而强行拆分。
* 父 Agent 不得替代任务文档中明确声明的角色。
* 实现 Agent 不得包办独立验收。
* 不得用重复测试伪造 Agent 独立性。
* 不得重复执行仍然有效的正式验证。
* 已确定被替代的旧职责不得因保守兼容无理由保留。
* 不得为了复用旧代码让新权威模型重新退化为旧表示。
* 不得自行发明用户可见阈值或业务规则。
* 不得用 Lint、编译或构建成功替代原始问题的行为验证。

## 完成前检查

* 请求分类是否正确？
* 是否读取了必要 Spec，而不是无目的扫描？
* 新的稳定结论是否进入正确的长期 Spec？
* 已失效的旧 Spec 是否同步更新？
* 同一语义是否存在多个事实源？
* 新权威路径是否真正接管职责？
* 被替代的旧机制是否完成清理？
* 保留的兼容层是否有真实理由？
* 是否存在未经依据新增的业务规则？
* 原始失败案例是否实际验证？
* Agent 分工和测试所有权是否落实？
* 验证范围是否最小但充分？
* 索引、任务状态和文档是否完成收口？
