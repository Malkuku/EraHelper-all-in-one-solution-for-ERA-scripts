# AI Slop Cleaner

## 定位

用于治理已经进入代码库的垃圾代码和技术债。

默认先审计，不直接修改。审计期间在仓库指定目录（无指定则为根目录）维护：

```text
AI_SLOP.md
```

`AI_SLOP.md` 是审计和用户审批阶段的工作清单，不是永久技术债档案。稳定结论最终应迁入迭代任务、Spec 或其他正式工程文档。

## 基本原则

* 删除优先于新增。
* 收敛优先于继续兼容历史结构。
* 不把“还有调用者”自动视为保留理由。
* 不为了清理而改变有效业务契约。
* 用户批准清理对象，Agent 负责沿真实依赖关系完成清理。
* 已被正式文档承接的信息不继续重复保存在 `AI_SLOP.md`。

## 1. 审计

优先读取项目索引、Spec/API、目标模块、测试和实际调用关系。

重点寻找：

* **重复职责**：同一业务语义在多个入口分别实现。
* **权威路径未收敛**：新机制已成为事实来源，但旧机制仍承担相同职责。
* **死代码**：无有效生产入口的代码、配置、SQL、flag、测试和文档。
* **无职责抽象**：纯透传 wrapper、单用途 helper、历史 adapter。
* **表示往返**：新模型重新转换成旧表示，只为了继续走旧加工链。
* **过期兼容层**：没有明确兼容对象、理由或退出条件的 shim。
* **边界错位**：业务语义落在错误层级。
* **回归缺口**：清理前无法保护关键行为。

不要只统计重复代码行；优先寻找重复事实源和失去职责的结构。

审计时先读取已有 `AI_SLOP.md` 和相关长期 Spec，避免重复提出已经审阅、接受或解释过的问题。

## 2. 维护审计清单

发现可靠问题后创建或更新 `AI_SLOP.md`。

每项保持简短：

```md
## AS-001 权威路径未收敛

- 范围：`search/highlight`
- 证据：统一段模型建立后，旧 `<em>` / sentinel / DOM 转换链仍继续存在。
- 问题：新抽象只包裹旧流程，没有真正替代旧职责。
- 建议：让统一段模型成为内部权威表示，删除失去职责的旧加工层。
- 风险：中
- 状态：待审阅
```

审阅阶段可使用：

* `待审阅`
* `待补充`
* `已批准`
* `暂缓`
* `长期保留`
* `不处理`

不要在清单中写长篇架构报告；只保留用户判断所需的证据、问题和建议。

## 3. 用户审阅

持续根据用户反馈更新 `AI_SLOP.md`。

只要本轮仍存在需要用户判断或进一步调查的条目，就继续补充证据和维护清单，不进入代码实施。

用户批准部分条目不代表整个实施阶段已经开始。直到所有影响本轮清理的决策都已解决，再根据最终清单统一生成实施任务。

用户批准的是条目及其语义清理边界，不是每个文件、函数和删除动作。

属于已批准项依赖范围的具体 helper、配置、测试和死代码无需重复审批；新的独立问题应登记为新的 `AS-*` 项。

## 4. 审阅收口与正式化

审阅闭合后，不直接把 `AI_SLOP.md` 当成实施文档。

### 批准清理的项目

将所有 `已批准` 项整理到仓库正式的迭代任务中，明确：

* 清理目标和范围。
* 应收敛到的权威路径。
* 需要删除或合并的旧职责。
* 必须保持的行为。
* 验证范围。

确认迭代任务已经完整承接这些信息后，从 `AI_SLOP.md` 删除对应的预执行条目。

后续实施状态、验证证据和完成记录由迭代任务维护，不再回写一份重复历史到 `AI_SLOP.md`。

### 预期不处理的项目

如果 `长期保留`、`不处理` 或长期 `暂缓` 来自稳定的项目约定、架构选择、兼容要求或已知限制，应把其原因写入对应长期 Spec、ADR、API 或架构文档。

记录重点是：

* 为什么当前结构是有意保留的。
* 它承担什么真实职责。
* 什么条件下需要重新评估。

正式 Spec 已承接后，从 `AI_SLOP.md` 删除对应条目。

这样后续审计应先读取这些长期事实，不重复向用户询问已经明确决定的项目习惯。

纯误报且不存在值得长期记录的工程事实，可以直接从清单移除。

### 未解决项目

真正尚未决策或计划以后处理的债务继续保留在 `AI_SLOP.md`。

如果所有内容都已经迁入正式工件或被解决，则删除 `AI_SLOP.md`。

## 5. 清理

按照迭代任务中批准的范围实施，通常按风险从低到高处理：

1. 已确认 dead code。
2. 已被权威路径替代的旧实现。
3. 重复业务语义。
4. 无职责 wrapper / adapter / helper。
5. 不必要的数据表示往返。
6. 命名、错误处理和测试缺口。

新模型已经成为内部权威表示时，调用方应优先直接消费它。

不得把新模型重新序列化成被替代的旧表示，仅为了继续复用旧加工链。

不要为了删除一个坏抽象，再创建两个新的抽象。

实施过程中发现新的独立债务时，重新登记到 `AI_SLOP.md`，供下一轮审阅；不得静默扩大当前迭代范围。

## 6. 验证

每项清理按最小充分范围验证：

* 有效行为仍然成立。
* 原始失败案例没有回归。
* 被取缔路径不再作为生产权威路径生效。
* 删除内容没有真实调用、动态注册或协议入口。
* 相关测试通过。

Lint、typecheck、build 和关键词检索只能作为辅助证据。

如果所谓清理只是增加统一入口，而旧职责几乎全部继续存在，不得视为完成。
